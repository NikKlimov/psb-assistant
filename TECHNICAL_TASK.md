# Техническое задание (ТЗ) на прототип ИИ-ассистента по продуктам ПСБ

## 1. Цель проекта
Разработать работающий прототип (веб-интерфейс или Telegram-бот) интеллектуального поискового ассистента по розничным продуктам ПСБ. 
Ассистент должен на основе данных с сайта `https://www.psbank.ru/` отвечать на сложные сравнительные вопросы пользователей (например, *«Что выгоднее — вклад в юанях или накопительный счет?»*) и предоставлять ссылки на первоисточники.

---

## 2. Источник данных (Критическое ограничение)
- **Разрешено:** Парсить только публичные страницы домена `www.psbank.ru` с соблюдением правил `robots.txt` (без агрессивного DDoS-краулинга).
- **Запрещено:** Использовать готовые датасеты, API банка (их нет) или сторонние агрегаторы (Бробанк, Banki.ru и т.п.).
- **Минимальный охват:** Продукты из категорий **«Вклады»**, **«Кредиты»** и **«Банковские карты»** (минимум 3 страницы с детальными условиями).

---

## 3. Функциональные требования

| № | Требование |
|---|------------|
| 1. | **Поиск по продуктам:** Пользователь вводит запрос, система возвращает список релевантных продуктов с кратким описанием и ссылкой на страницу. |
| 2. | **Сравнительный анализ:** Возможность сравнить 2–3 продукта по ключевым параметрам (ставка, срок, кешбэк, комиссии, валюта). |
| 3. | **Ответы на "сложные" вопросы:** Система корректно обрабатывает запросы, связанные с социальными категориями (например, участие в СВО, пенсионеры, жители Дальнего Востока) и продуктами в нестандартных валютах (юань). |
| 4. | **Обязательная валидация:** Каждый факт в ответе должен сопровождаться `source_url` — прямой ссылкой на страницу ПСБ, откуда был взят этот факт. |

---

## 4. Технические ограничения и архитектурные требования

Прототип должен быть написан на **Python**. Следующие правила обязательны для проверки инженерного подхода:

### 4.1. Запрет на "тяжелые" фреймворки
- **Запрещено** использование LangChain, LlamaIndex, AutoGPT, Haystack и подобных высокоуровневых фреймворков для агентов.
- **Разрешены:** `requests`/`aiohttp`, `BeautifulSoup`/`lxml`, стандартная библиотека.

### 4.2. Кеширование данных (Resilience)
- Парсинг страниц должен сопровождаться дисковым кешем (SQLite или JSON).
- Повторный парсинг одной и той же страницы возможен только по истечении **24 часов** или принудительно (флаг `--force-update`).

### 4.3. Абстракция LLM-провайдеров
- Код должен поддерживать **минимум две** различные модели/API.
- *Пример:* GigaChat, YandexGPT, локальная Qwen/LLaMA, или OpenAI (с учетом ограничений).
- Смена модели должна происходить через переменную окружения (`LLM_PROVIDER`) без правки кода.

### 4.4. Обработка фильтров контента (Спецоперация/СВО)
- Многие российские модели имеют встроенные фильтры безопасности, которые могут блокировать ответы на запросы об "участии в СВО" или "военных операциях".
- **Инженерное требование:** При получении ошибки фильтрации (или пустого/отказного ответа) система **не должна падать**. Она обязана:
  1. Залогировать факт блокировки.
  2. Переключиться на резервную модель (из п. 4.3) или выдать заранее подготовленный ответ из базы знаний (например: *«Для уточнения льготных условий рекомендуем обратиться в отделение банка»*).

### 4.5. Строгая валидация выходных данных (Pydantic)
- Ответ LLM обязан соответствовать жесткой Pydantic-схеме. Пример структуры:
  {
    "product_name": "Накопительный счет",
    "params": {"ставка": "10%", "срок": "Без ограничений"},
    "source_url": "https://www.psbank.ru/...",
    "risk_warning": null
  }
- **Правило:** Если ответ невалидный → выполняем повторный запрос с `temperature=0.0` (максимум 2 ретрая). Если повтор не помог — отдаем пользователю сообщение об ошибке, а не "галлюцинацию".

## 5. Требования к качеству кода (Культура разработки)

Ваш код будет оцениваться по чек-листу ниже. Это не "хотелки", а критерии приемки прототипа.

### 5.1. Инженерия данных (Парсинг)
- [ ] Реализованы повторные попытки (Retry) с экспоненциальной задержкой при HTTP-ошибках (429, 503).
- [ ] Для каждой категории продуктов выделен отдельный класс/модуль-парсер (например, `CardParser`, `DepositParser`).
- [ ] Падение одного парсера не ломает весь краулер (используйте `try/except` на уровне обработки страницы).

### 5.2. Работа с LLM
- [ ] Реализован единый интерфейс `BaseLLMClient`, наследники реализуют методы `generate()`.
- [ ] Промпты вынесены в отдельные файлы (или константы), а не захардкожены внутри функций.
- [ ] Системный промпт жестко требует возврата **только валидного JSON** и указания `source_url`.

### 5.3. Архитектура и стабильность
- [ ] Весь код покрыт аннотациями типов (Type Hints) и проверяется Pydantic-схемами.
- [ ] Настроено структурированное логирование (с уровнями INFO, WARNING, ERROR).
- [ ] Написаны **минимум 2 юнит-теста** (например, тест на валидатор JSON и тест на парсер с мок-данными).
